# ADR-0020 — Discount codes: scoped, server-computed, concurrency-safe, floored at zero

**Status:** Accepted · 2026-09-01 · **revised 2026-09-01** (scope, code format and redemption records added) · supersedes the no-discount-field ruling of [ADR-0005](0005-money-in-toman.md)

**Context:** ADR-0005 refused an `Order.discount` field on the grounds that a money field with no mechanism behind it is a bug factory. That was right at the time — there was nothing that could legitimately write it. A discount code model is that mechanism, so the objection is answered rather than overruled. Discounts are also a place where a shop leaks money in three specific ways: a browser that gets to say what the total is, a single-use code that two concurrent checkouts both spend, and a per-user limit that nothing records enough history to enforce.

**Decision:**

**Model `DiscountCode`:** `code` · `kind` (`percent` | `fixed`) · `value` · `scope` (`all` | `selected`) · `products` (M2M → `Product`) · `max_uses` (nullable = unlimited) · `used_count` · `per_user_limit` (nullable) · `min_order_amount` (nullable — compared against the order **subtotal**, before any discount) · `valid_from` / `valid_until` (both nullable) · `is_active` · `created_at`.

**Code format.** `varchar(8)`, `UNIQUE`, **stored uppercase**, with a `CHECK` matching `^[A-Z0-9]{4,8}$` — letters and digits only, four to eight characters. Input is normalised to uppercase before lookup, so a customer typing `nowruz` finds `NOWRUZ`. The format exists so a code can be read aloud, typed on a phone keyboard without a shift key, and printed in a Telegram message without ambiguity; the database enforces it rather than the admin form, because the admin form is not the only thing that will ever write a row.

**Scope.** `scope='all'` discounts the whole order. `scope='selected'` discounts **only the eligible lines** — the lines whose plan belongs to one of the code's `products`. The discount is computed against the **eligible subtotal**, never the order subtotal. A 20% code scoped to one product on a cart holding that product and two others takes 20% of that one product's line total, not of the cart.

**Model `DiscountRedemption`:** `discount_code` (FK) · `user` (FK) · `order` (FK, **UNIQUE**) · `amount` · `created_at`. It exists because **`per_user_limit` cannot be enforced without it** — a counter on the code knows how many times it was spent but not by whom, and reconstructing that from order rows means scanning order history on every checkout. It doubles as the audit trail of what each code actually cost: one row per redemption, with the toman figure that redemption took off. `UNIQUE` on `order` because one order redeems at most one code.

**Order gains** `subtotal`, `discount_code` (FK → `DiscountCode`, `PROTECT`, nullable), `discount_amount` (toman, default 0) and `total_amount`. `PROTECT` because a code that has been spent is part of an order's money history and must not be deletable out from under it.

**Computation, stated once and tested:**

1. `eligible_subtotal` = the sum of the line totals in scope — every line for `scope='all'`, only the lines whose plan's product is in `products` for `scope='selected'`. Line totals come from `effective_price` ([ADR-0021](0021-promotional-pricing.md)) × quantity, recomputed from the database.
2. **Percent:** `discount_amount = round(eligible_subtotal * value / 100)` to whole toman using **`ROUND_HALF_UP`**. Named explicitly because Python's default is banker's rounding, which would make a 5-toman half-unit land differently than an operator reading the same arithmetic expects.
3. **Fixed:** `discount_amount = min(value, eligible_subtotal)`.
4. **Clamped:** the result is capped so `total_amount` can never fall below zero. A 200%-typo or a fixed discount larger than the cart reduces the total to zero and no further. There is no negative total and no store credit.

**The rules, each of them tested:**

- **Server-side only, at checkout only.** The code is validated and the discount computed from database values. Nothing the browser sends is an input to the amount — the client submits a string, and the server decides what, if anything, it is worth. A discount is never stored in the cart ([ADR-0018](0018-shopping-cart-and-guest-checkout.md)), which holds plan and quantity and nothing else.
- **`used_count` is incremented under `select_for_update` inside the order-creation transaction**, in the same transaction that creates the order, its items and the `DiscountRedemption` row. Two checkouts racing on a single-use code serialize on the row lock; the loser is rejected on the re-checked limit. A code with `max_uses=1` cannot be spent twice, and this is a concurrency test, not a code-review promise.
- **`per_user_limit`** is checked in the same locked section, by counting the user's `DiscountRedemption` rows for that code.
- **Stacking:** a code applies **on top of promotional pricing**. It discounts what the customer would actually pay — the promotional price, not the list price — because that is what "20% off" means to the person reading it, and because the alternative silently gives a smaller discount than the number on the banner. *Named future option:* a per-code `excludes_promo_items` flag that drops promotionally-priced lines out of the eligible subtotal. **Flips when** a promotion plus a code demonstrably sells something below cost — not before; a flag nobody has needed is a branch in the money path with no test behind it.
- **All of it is managed from the admin panel.** The operator creates codes, sets `kind` and `value`, chooses `scope`, and picks products when the scope is `selected`. There is no code-generation feature and no bulk import.
- **Stated invariant, asserted in tests and true of every order row:** `subtotal = Σ item price_snapshots`; `total_amount = subtotal − discount_amount`; `total_amount ≥ 0`; and where a code was used, `DiscountRedemption.amount = Order.discount_amount`. `subtotal` and `discount_amount` are snapshots, so editing a code's value, scope or product list later never rewrites what an old order charged.
- Money display follows `../design-language.md`: subtotal, discount and total are three distinct ledger lines, Persian digits, ASCII thousands separator, toman only, tabular figures.

**Alternatives considered:** **Compute the discount in the view from a posted amount** — the classic negative-total/free-order hole; rejected outright. **`used_count` incremented with an unlocked read-modify-write or a bare `F()` expression** — `F()` is atomic for the increment but cannot enforce the *limit*, so two racers both pass a stale `used_count < max_uses` check; the row lock is what makes the check and the increment one decision. **A counter with no redemption rows** (the previous version of this ADR) — it answered "how many times" but not "by whom" without scanning orders, which is exactly what `per_user_limit` needs on every checkout; the table that fixes it is four columns and also gives the operator a straight answer to "what did that campaign cost". **Free-text codes of any length and case** — rejected: case-sensitivity turns a typo into "invalid code" and a customer into a support message, and unbounded length invites codes nobody can read over the phone. **Percent discounts scoped by category rather than product** — rejected: categories are flat and coarse ([ADR-0014](0014-deliberate-simplifications.md)), and a product M2M expresses every category promotion the operator can currently run by selecting the products. **Coupons stay cut** — rejected: the mechanism now exists, and discount codes are the one promotion tool a shop this size actually uses.

**Consequences:** ADR-0005 stands entire on toman storage and its rial boundary; only its "no discount field" clause is retired. `Order.total_amount = Σ item price_snapshots` becomes `subtotal = Σ item price_snapshots`, and every place that recited the old invariant — data model, services, checkout tests — states the three-line version instead. Codes are one of two ways a price moves; the other is promotional pricing ([ADR-0021](0021-promotional-pricing.md)), and the two compose in exactly one stated order: promotion first, code second.
