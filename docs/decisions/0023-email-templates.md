# ADR-0023 — Email templates: hand-built tables, system fonts, wordmark set in type

**Status:** Accepted · 2026-09-02

**Context:** The shop's central obstacle is doubt about ever receiving the product (`design-language.md`), and the two messages that carry that doubt are the login code and the delivery notice. Both arrive as email, which is not the web: Outlook on Windows lays out with Microsoft Word's engine (no flex, no grid, no dependable float), Gmail and Outlook strip `@font-face` so **Estedad and Vazirmatn cannot travel**, Gmail's mobile app strips `<style>` for accounts it does not host, and most clients block remote images until the reader allows them.

**Decision:** Emails are hand-written Django templates under `templates/email/`, one layout (`base.html`) plus three files per message — `<name>.subject.txt`, `<name>.txt`, `<name>.html` — so every Persian string lives in a template and none in Python. Layout is `<table>`; critical styling is inline, with `<style>` carrying only media queries and client resets. Two components are includes because retyping them is where mistakes live: `_button.html` (a table-cell button, since Outlook ignores background and padding on an anchor) and `_fact.html` (the ledger line, whose dotted leader is a cell's `border-bottom` — the one leader technique Outlook renders).

Three adaptations of the design language, forced by the medium:

- **The wordmark is set in type, not placed as an image.** A blocked image would render a broken box on the most trust-sensitive message the shop sends. The design is typographic anyway.
- **Font stack is `Vazirmatn, -apple-system, "SF Arabic", "Segoe UI", "Noto Sans Arabic", "Noto Naskh Arabic", Tahoma, Arial`** — the brand's own body face first, so anyone who has it installed gets the real thing, then each platform's own Persian face, with **Tahoma last as the safety net**. The first draft led with Tahoma and the result was rejected on sight: it is the face that makes Persian email look like 2005, and it was overriding better faces on every platform that had one. What survives the crossing is the *metric* rule, not the face: 1.9 line-height on prose, `letter-spacing: 0`, no italic, no `text-transform`.
- **Colour and geometry carry over unchanged** — warm stone, one teal accent, hairlines instead of shadows, optical button padding with the block-end lighter (Persian ink sits low in the line box). Radius is **10px throughout**, not the site's 4px button: at email sizes 4px reads as an artifact rather than as a shape, and one radius across card, panels and button is what makes the result read as soft rather than as a form. Outlook drops radii entirely; square is the acceptable degradation, and VML is not worth ten lines of conditional markup for a corner. The amber notice is tint + hairline + dark text, never a saturated fill — the same rule the site's badges follow, because a saturated block reads as an alarm and this is a deadline. **Amber still means time and only time**: the code expiry and the delivery-link expiry, nothing else.

Every message is sent `multipart/alternative` through `apps.core.email.send_templated_email`. The subject is whitespace-collapsed before it becomes a header, so a newline arriving through context cannot inject one. `/dev/emails/` renders any template in a browser and 404s unless `DEBUG`.

**Alternatives considered:** MJML or Foundation for Email (a Node build step and a dependency tree for four templates, and the output still needs the same hand-checking); a hosted template builder (the design leaves the repo, and it is another foreign account to lose); `<div>` layout with modern CSS (correct in Gmail, collapsed in Outlook); shipping HTML only (worse spam scoring, and unreadable in text-only clients).

**Bug this shipped, and the guard it earned:** Django compiles `{# ... #}` with a regex that has no `re.DOTALL`, so a comment crossing a newline is **never lexed as a comment** — it is emitted as literal text. This reached a customer's inbox in the delivery email, and an audit then found the same mistake twice in the site's own `templates/base.html`, shipped since S1. Every template in the project is now scanned by a test; multi-line notes must use `{% comment %}`.

**Consequences:** Emails will never look exactly like the site, and that is accepted — the metrics and the palette are what carry the family resemblance, not the typeface. Each new message costs three files, which is the price of keeping Persian copy out of Python. Rendering is verified by tests (every template compiles, no unrendered placeholder escapes, no web font sneaks back in, both MIME parts present) but *appearance* is not: it is checked by eye in the preview route and by sending to a real inbox. The OTP is rendered in Persian digits, so **the login form must normalise Persian digits to ASCII before comparing** — otherwise a customer who copies the code they were shown cannot log in. That belongs to S2 and is recorded in `open-questions.md`.
