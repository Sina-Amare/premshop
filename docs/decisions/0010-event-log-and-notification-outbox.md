# ADR-0010 — Append-only event log + notification outbox (and the accepted crash gap)

**Status:** Accepted · 2026-09-01

**Context:** Three promised features (public tracking timeline, SLA pause math, delivery metrics) need per-transition history; notifications must never roll back a delivery, never double-send, and legitimately re-send after a replacement.

**Decision:**
- `OrderItemEvent`: append-only, written **inside** every transition transaction. It is the timeline, the audit trail, the metrics source, and it is never purged.
- Events are dispatched by a thin in-process `events.emit()` registered via `transaction.on_commit` — no Django signals, no pub/sub framework. Its only job is creating `Notification` outbox rows.
- Outbox: per-(occurrence, recipient, channel) rows with a globally-unique `dedupe_key` (`{occurrence}:{recipient}:{channel}`); `user = NULL` means the operator; channels are exactly `email` and `telegram` (IN_APP cut — the order pages are the in-app surface; SMS deferred, phone field kept). Sender uses `select_for_update(skip_locked=True)`; fixed backoff ladder (now, 1m, 5m, 15m, 1h, 6h → failed); non-retryable errors fast-fail. Operator order/payment alerts go out on **both** channels; a beat-driven external dead-man heartbeat alarms from outside the app when the pipeline itself dies.
- **Accepted trade-off:** enqueueing on `on_commit` means a process crash in the commit-to-enqueue gap silently drops that occurrence's notifications. Accepted at this volume — the overdue digest, the operator queue, and the heartbeat are the backstops. Do not "fix" this ordering without reopening this ADR.

**Alternatives considered:** `unique_together(order_item, event_type, channel)` dedup (NULL-hostile for order-level events, and blocks the legitimate second "delivered" after a replacement); classic in-transaction outbox (stronger guarantee, more machinery than this volume justifies).

**Consequences:** A notification failure can never affect order state. Re-sends are modeled by new occurrences, never by relaxing uniqueness.

**Amendment — 2026-10-26.** Order history now has database enforcement: its PostgreSQL trigger rejects UPDATE and DELETE, and protected foreign keys preserve its item and order. Creation and unpaid cancellation write their events atomically. No dispatcher or notification consumer is installed for these unpaid actions; creation must not alert the operator as if payment had arrived. The later outbox design and its accepted crash gap are unchanged.

**Amendment — 2026-11-03: purchase confirmations discovered from committed orders.** C1 is restored as a retainable email purchase record, not a payment result. New placements freeze the account email; existing orders retain an empty field and are never backfilled or confirmed. Notifications polls committed eligible orders each minute and creates a uniquely keyed row with frozen recipient, subject and both bodies. No order callback or `core.events` is involved, so a missed tick or crash before discovery cannot lose a new purchase confirmation. This replaces the accepted commit-to-enqueue gap for C1 only; future event-driven messages remain unbuilt. One render failure logs only order ID and exception class and does not block other discoveries or sends.

Each send has its own transaction and holds its notification lock through SMTP. The previous row's successful result commits before another send begins. A durable singleton quota cooldown is locked before sending, serializing confirmation senders. The first guard refusal sets a shared 15-minute wait and bulk-postpones all due pending rows without spending attempts; the tick stops. New arrivals and newly due retries honor that shared wait too, limiting blocked confirmation attempts to 96 a day. The lower-priority reserve and unavailable-accounting refusal remain in core.

C1 uses six attempts: now, then delays of 1m, 5m, 15m, 1h and 6h after successive failures, then failed. Permanent SMTP rejections also take this ladder, replacing the original non-retryable fast-failure rule for this message. Uncertain results retry automatically; an occasional duplicate after acceptance without a recorded result is accepted. Uniqueness prevents duplicate rows, not duplicate SMTP delivery. Failed or waiting confirmations are visible read-only in the panel; no manual resend is provided because the customer order page holds the saved text. An SMTP acceptance is not proof of inbox delivery. Other order state is never changed by mail.

**Amendment — 2026-11-09: customer order email updates.** Explicit service calls now register after-commit callbacks for verified payment, requested input, delivery/redelivery, rejected replacement, supply delay, cancellation and recorded refund execution. Payment uses its verified payment ID; item messages use their distinct history IDs. The existing outbox adds a template discriminator, preserving every frozen confirmation and its retry semantics. Confirmation discovery checks that discriminator, so an update cannot suppress the purchase record. All emails share the existing quota cooldown; non-confirmation updates fast-fail SMTP 5xx rejections and retry transient/uncertain failures. A callback catches failures and logs only identifiers and the exception class; other callbacks continue. The accepted crash gap remains for these updates. Delivery uses the signed-in order link until the separately planned magic-link flow exists; no credential, input, operator note or bank reference reaches a message. Telegram, sign-in codes, timed input handling and gateway failures remain separate work.

**Amendment — 2026-11-09: which update failures are permanent.** The rule above was too wide. A 5xx on login, sender, connection or DATA describes the shop's own mail account (a rotated key, an unverified sender domain) and would have failed every update in that outage on its first attempt, with no resend. Updates now fast-fail only when every recipient is refused with a 5xx; every other failure takes the six-attempt ladder, as confirmations do. A message rejected for its content therefore spends five more attempts before it fails; the body is a frozen shop template, so such a rejection is shop-wide too. An outage longer than the ladder still fails rows. Revisit if the provider's replies show a DATA-stage code that is reliably about one message.
