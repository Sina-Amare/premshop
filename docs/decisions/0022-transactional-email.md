# ADR-0022 — Transactional email: SMTP2GO relay, env-driven, encryption derived from the port

**Status:** Accepted · 2026-09-02

**Context:** Authentication is email + one-time code (ADR-0012), so email is not a notification channel — it *is* the login system. A message that is delayed, spam-filed or silently dropped is a paying customer who cannot reach the credentials they bought. The shop is Iran-hosted and Iranian ISPs filter outbound SMTP; the operator has no foreign card, so any provider that must be paid is a provider that will eventually be lost. Before this step `prod.py` selected Django's SMTP backend while nothing set `EMAIL_HOST` — production would have handed every login code to `localhost:25`, which is both absent and the one port measured as blocked.

**Decision:** Transactional mail goes through **SMTP2GO** (free tier, 1000/month, 200/day) over Django's stock SMTP backend, with `premshop.ir` as a verified sender domain — DKIM and a custom return-path published as CNAMEs, which is what buys DMARC *alignment*. All connection settings come from the environment (12-factor), so changing relay, port or credentials is a restart rather than a deploy.

Four rules are enforced in code rather than documented:

- **`EMAIL_PORT` is the only encryption knob.** `EMAIL_USE_SSL` is derived as `port in {465, 8465, 443}` and `EMAIL_USE_TLS` as its negation. Django raises `ValueError` when both are true — and only at send time, i.e. on a real login. Deriving them makes the pair unrepresentable instead of merely discouraged.
- **`EMAIL_TIMEOUT = 10`.** Django's default is `None`: no timeout. A blackholed Iran-to-Europe connection would otherwise pin a web worker indefinitely on the login path.
- **`prod.py` fails closed** on a missing `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`, because Django guards `login()` with `if self.username and self.password:` — a blank password connects *anonymously* and every message is rejected. Silent total login outage becomes refusal to boot.
- **`DNS_NAME._fqdn` is pinned** to `premshop.ir`. Django derives both the `Message-ID` domain and the SMTP `EHLO` name from `socket.getfqdn()`; unpinned it stamped the developer laptop's hostname into the first real send, and the lookup runs before the socket exists so `EMAIL_TIMEOUT` cannot bound it.

The root SPF record is deliberately left as `v=spf1 include:spf.improvmx.com ~all`. SMTP2GO is **not** added to it: the CNAME'd return-path subdomain carries SMTP2GO's SPF, and an extra `include:` would spend one of the 10 permitted lookups for nothing. `_dmarc` is published at `p=none` for the aggregate reports, which are the only instrument that shows whether a code was delivered. `aspf=s` must never be added — strict SPF alignment would fail every SMTP2GO message.

**Alternatives considered:** Iranian relays (payable in toman, but a foreign-hosted fallback is wanted precisely because a domestic one shares the failure mode of a national outage; kept as the documented fallback); ImprovMX SMTP (excluded from its free plan); Gmail SMTP (personal account, rejected by the brief); direct-to-MX from the app server (no owned PTR record — an immediate spam classification); a `MailProvider` interface (rejected on the same grounds as ADR-0013: one implementation is not an abstraction, and four environment variables already *are* the switch).

**Consequences:** Mail sends today, verified end to end from an Iranian IP: SMTP2GO answers on 2525/8025/587/465/8465/443/80, port 25 times out. Round trip is ~2.6s, which is tolerable synchronously and is one more reason the outbox and Celery arrive at S6 — until then a relay stall costs a request, not just a message. Free-tier ceilings are hard rejections, not queues, so the send path needs a monthly counter and an operator alert before launch; the operator alert must travel over Telegram, never email, because email is the thing that will have broken. SMTP2GO's activity log retains only 5 days, so the app must record its own send audit trail rather than depending on the provider's dashboard. Port reachability was measured from a home connection; Iranian data centres route internationally by a different path, so the sweep is re-run from the production host at S6b before launch.

**Amendment — 2026-11-02: send accounting and the interim quota warning.** Every templated send inserts one `core.MailAttempt` per recipient, then counts the rolling last 24 hours and the current allowance month. No quota row is locked. Concurrent requests can exceed the local ceiling; this is a soft guard, not a provider guarantee. The attempt rows commit over a separate autocommit connection to the same database, so password recovery's session transaction cannot hide or roll them back. Database connection and statement timeouts bound bookkeeping waits. There is one table, no Redis quota counter or quota-state row. In-flight, accepted and uncertain attempts count; blocked attempts and definite transport failures do not. Accepted records SMTP acceptance, never inbox delivery. A lost post-send result remains conservative in-flight accounting. Attempts expire after 90 days.

Login codes, password-recovery codes, sign-in alerts and password-change notices may use all 200 daily / 1,000 monthly units. Other mail stops at 180 daily / 900 monthly, preserving 20 daily / 100 monthly for security mail. Accounting failure never prevents a security send or changes an accepted send into failure; genuine SMTP failures still reach the caller. Other mail refuses when accounting is unavailable. A known exhausted quota returns temporary unavailability to code-request/recovery views; notices still cannot undo sign-in or a password change. No retry queue is introduced here.

`EMAIL_QUOTA_RESET_DATE` is the UTC start date of the provider allowance period at activation. Monthly boundaries retain its day of month, clamped for shorter months. `EMAIL_QUOTA_STARTING_USAGE` adds already-used recipients missing from the app log, only during that initial period. Before activation, reconcile that date and usage against the provider dashboard, include all senders sharing the allowance, and allow a full 24 hours of app records before relying on the daily estimate. Missing/invalid baseline settings make accounting unavailable. Never reset these values on an ordinary restart.

Until S6 provides the operator's Telegram alert, the warning is a staff-panel banner, never email: at 80% of either limit, at reserve protection/exhaustion, or when accounting is unavailable. The read-only mail list is its reader and the support lookup for a code request. Exact-address search submits by POST and redirects with a keyed fingerprint, so the address does not enter the results URL. Stored metadata is limited to template, keyed recipient fingerprint, timestamps, outcome, exception class and numeric SMTP status. No address, message/context, code, token, URL, credential or customer input is retained; error logging carries only the exception class without traceback or reply text.

The relay remains SMTP2GO with the verified `@premshop.ir` sender. The original claim about daily excess is corrected: the [Free Plan documentation](https://support.smtp2go.com/hc/en-gb/articles/223087947-Free-Plan), checked 2026-11-02, says daily excess may queue, while monthly excess is rejected and not queued. The application's own guard refuses at its daily ceiling; accounting failure, concurrency or sends outside the app can still encounter the provider's behavior. Confirmation mail, outbox delivery and its retry policy remain separate work.

**Amendment — 2026-11-12: the reserve after one way in per account.** Customers no longer have a password (ADR-0012, 2026-11-12), so recovery codes, sign-in alerts and password-change notices are no longer sent. Sign-in codes and Telegram link notices are the mail that may use the reserve.
