# ADR-0024 — Auth implementation: cache-backed codes, one flow for login and registration, no separate password reset

**Status:** Accepted · 2026-09-04 · implements [ADR-0012](0012-auth-email-otp.md)

**Context:** ADR-0012 settled the *shape* of authentication — email as identity, login by password or emailed one-time code, OTP doubling as verification, a sign-in alert on any OTP session opened against a passworded account. This records what building it decided.

**Decision:**

- **`accounts.User` is migration 0001 of the whole project.** Django permits swapping `AUTH_USER_MODEL` only while the database has no tables; afterwards it is a hand-rebuilt schema on a live system holding real orders. `accounts.0001` depends on nothing from this project, which is the ordering rule made checkable.
- **Email uniqueness is enforced twice.** `unique=True` catches exact duplicates; a functional `UniqueConstraint(Lower("email"))` catches `Ali@` versus `ali@`. The manager lowercases on the way in, but the manager is not the only door — the admin, a shell and a future import all reach the table directly, so the guarantee lives in the database. Both were verified by reintroducing the duplicate and watching each index fire.
- **Codes live in the cache with a TTL, not in a table.** An expired code should evaporate rather than accumulate as rows for someone to sweep, and there is no state worth keeping afterwards: the audit trail that matters is the session, not the code that opened it. Stored keyed-hashed, so a cache dump or a monitoring tool does not display a live credential.
- **One flow does login AND registration.** A code goes to any valid address; verifying it creates the account if none exists. This is ADR-0012's inline-checkout idea generalised, and it removes the user-enumeration oracle for free — there is no "no such user" branch to time. The abuse it opens, making the shop mail a stranger, is bounded by the rate limits.
- **Rate limits (owner-approved 2026-09-04):** 3 code requests per address / 15 min · 10 per IP / hour · 10 login attempts per address / 15 min · 30 per IP / hour · a code burns after 5 wrong guesses. Per-identity *and* per-IP, because either alone has an obvious hole: an address limit lets one machine spray a thousand addresses, an IP limit lets a botnet hammer one account. A wrong guess re-stores the code without extending its deadline, so guessing cannot buy time.
- **OTP lifetime is 10 minutes, not the 5 the notification contract carried.** Email is not SMS: the relay takes ~2.6s but delivery plus the customer noticing can take a minute, more on Iranian mobile data. Five minutes turns ordinary slowness into "code expired" on the login path, which is the highest-cost failure this shop has. The code is single-use, rate-limited, and sent to the address that already controls the account, so the widened window buys an attacker almost nothing. `notifications-and-bot.md` C12 and the Telegram TTL were updated to match.
- **No separate password-reset link flow.** *This is a deliberate cut from the S2 scope.* A reset link would be a second single-use token system, with a second expiry policy and a second email, to reach an outcome the code flow already reaches: a customer who has forgotten their password logs in with a code and sets a new one on the account page, which renders `SetPasswordForm` (no current password asked) when the account has none. One mechanism, one set of rules to get right.

**Amended after the owner's S2 review (2026-09-05):**

- **The code page is six cells with a live countdown and a resend button.** Progressive enhancement: the server's single `code` field is unchanged and still works with JavaScript off; six cells drive it when JavaScript runs. The sixth digit submits by `fetch` with `Accept: application/json`, and the same view answers JSON when asked — one endpoint, content-negotiated, no second API surface. Success flashes green then navigates; a wrong code shakes, clears and refocuses without leaving the page. The countdown is seeded from **seconds remaining**, never an absolute server time, so a customer whose PC clock is wrong still sees the right number. Resend has a 60-second cooldown as a courtesy; the 3-per-15-minutes limit is the defence.
- **A cache outage renders a Persian 503, never a traceback**, via one `process_exception` middleware; `/healthz` checks the cache and reports `degraded` when it cannot — it had reported "ok" while nobody could log in.
- **The password rules are shown before they bite**, in one line matching the four validators; the phone is editable on the account page (normalised to the 11-digit `09` form); the header icon goes to the account or to code login by session state.
- **The brand is written `PremShop`, in Latin, everywhere** — sender name, subjects, email masthead, site header. One name, one spelling; the Latin form is the one anchor in an inbox of Persian subjects.
- **A password-reset link flow is still not built.** The owner reviewed the cut and did not ask for it.

**Alternatives considered:** an OTP model with a cleanup task (rows to sweep, nothing gained); a separate registration form (a second flow to keep in step, and it hands back the enumeration oracle); silently dropping codes for unknown addresses (the response time still answers the question); `CITEXT` for case-insensitive email (a PostgreSQL extension to install and a column type to migrate, where a functional index does the same work); Django's built-in `PasswordResetView` (see the cut above).

**Consequences:** Anyone can make the shop send mail to any address, bounded by the limits — acceptable at 200 sends/day, and the reason the per-IP limit exists. Codes vanish if the cache is flushed, which reads to a customer as "the code expired": correct behaviour, but it means a Redis restart during a login is a retry, not an error. Tests run against locmem so CI needs no Redis daemon. The sign-in alert cannot fail a login: the customer is already authenticated, and refusing that because a notification bounced would turn a mail problem into a lockout.

**Left for later:** Telegram-delivered codes (S8, needs linking); operator 2FA (S6b); a monthly send counter and quota alert before launch. Deliverability to an Iranian mail host is a **knowingly waived** gate — Gmail is proven, an Iranian provider was never tested.
