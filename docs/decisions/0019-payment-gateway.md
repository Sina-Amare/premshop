# ADR-0019 — An Iranian payment gateway is the rail; verify is server-side and confirmation is idempotent

**Status:** Accepted · 2026-09-01 · supersedes [ADR-0006](0006-card-to-card-payment-design.md)

**Context:** Card-to-card was chosen as the only rail available before Enamad. It cost the customer a bank-app detour and a screenshot, cost the operator a daily manual reconciliation against a bank app, and made every multi-product purchase a separate transfer. An Iranian gateway (Zibal-class) removes all three, and it removes the class of failure ADR-0006 spent most of its rules defending against: money arriving that matches no order. It introduces a different class — the browser is now part of the payment path, and the browser is controlled by the person paying.

**Decision:**

**The rail.** Checkout initiates a payment with the gateway, the customer is redirected to the gateway's page, and the gateway returns them to a callback URL. `Payment.method` stays an enum for the record (`gateway` | `manual`).

**Payment state machine** (replaces ADR-0006's; the contract is `../state-machine.md`):
`created → initiated → verified | failed | abandoned`, plus `created → verified` for the manual fallback below.

Non-negotiable, and stated in the state machine document:

1. **Server-to-server verify is the only source of truth.** The parameters on the browser redirect — status, amount, order id, whatever the gateway appends — are attacker-controllable and are never a confirmation. They select which payment to verify; they never decide its outcome.
2. **Verify compares the gateway-reported amount against the order total and rejects a mismatch.** An order is never confirmed for less than it costs. A mismatch fails the payment loudly and alerts the operator; it is not rounded, tolerated, or treated as a shortfall.
3. **Confirmation is idempotent, by a row lock and a re-read.** `payments.confirm_payment` takes `select_for_update` on the `Payment`, re-reads its status **under that lock**, and returns the payment unchanged if it is already `verified`. That — not an unlocked `if not payment.verified` check — is what makes a repeated callback, a refresh, a back-button replay, or a callback racing the inquiry task produce exactly one confirmation, one set of item transitions, and one `payment.verified` event.
4. **`Payment.idempotency_key` (UNIQUE) is a different mechanism with a different job.** It is the key sent to the **gateway** on the initiate call, so a retried initiate cannot create two payment requests upstream. It plays no part in confirmation; the lock-and-re-read above is the whole of that guarantee.
5. **A Celery beat task inquires on stuck payments, and this is mandatory.** Payments sitting in `initiated` longer than `SiteSetting.gateway_timeout_minutes` (default 15) are put to the gateway's inquiry/status API; one the gateway reports as paid is confirmed by that task on exactly the same path a callback would take. This covers the failure that actually loses money: the customer paid, the network died before the redirect, and without the job the money is taken and the order is dead.
6. **`abandoned` is reached only by that beat task**, after an inquiry says the payment was never completed. Nothing abandons a payment on a timer alone.

**Two clocks, two fields, never conflated.** `gateway_timeout_minutes` above is the lost-callback net and nothing else. The separate `SiteSetting.unpaid_order_ttl_hours` (default **24**) is how long an order may sit in `PENDING_PAYMENT` with no verified payment before the sweep cancels it with `cancel_reason = expired_unpaid`. The sweep **always skips an order whose payment is still `initiated`** — never cancel while money may be moving; it cancels once that payment lands in `failed` or `abandoned`. Twenty-four hours is deliberate rather than generous: the failed-payment message tells the customer their order is still waiting and hands them a retry link, and a thirty-minute window would make that promise a lie.

**Manual fallback (`method='manual'`).** An operator-only admin action, "record payment received outside the gateway", requiring a free-text reference note. It produces the same confirmed `Payment` and the same item transitions as a gateway verify, enters `verified` directly from `created` with the operator as actor, and is listed separately in the reconciliation view. It is **not customer-facing**: no receipts, no unique amounts, no customer "I paid" submission, no revive path. It is retained for three reasons worth writing down — the shop must be able to sell during the Enamad wait; Iranian gateway outages are routine rather than exceptional; and the brief's own risk #3 is having exactly one way to take money on day one.

**Refunds.** Prefer the gateway's refund API where the provider supports it; otherwise a manual bank transfer. Either way the `Refund` ledger gate still stands between `CANCELLED` and `REFUNDED` — no item reaches `REFUNDED` without an executed `Refund` row — which is [ADR-0003](0003-order-status-on-item-seven-states.md)'s rule and assertion A12 of `../state-machine.md`, not a payment-rail detail. The row now records the gateway refund reference alongside the bank reference.

**A refund message names no card.** A gateway refund returns to the original card automatically and we never learn its digits. The customer-facing refund message therefore carries the route-agnostic `{refund_ref}` and nothing more: there is no `{destination_last4}` placeholder, because that field does not exist for a gateway refund and the manual route's destination is not something to echo back at the customer.

**Deleted with the old rail.** Unique-amount allocation and its partial unique index; the 72h amount quarantine; receipt image upload, private storage and retention purge; the customer "I paid" submission; near-miss shortfall matching; `paid_amount`-vs-`unique_amount` reconciliation against a bank app; the `UnmatchedTransfer` ledger; revive-from-expired; and `SiteSetting`'s destination-card slots and `active_card`.

**Build order consequence.** A gateway requires Enamad, and Enamad requires a live site with orderable products. So: cart + checkout creating `PENDING_PAYMENT` orders → legal pages → soft production deploy and the Enamad filing → gateway integration once approved. The manual fallback is what the operator sells with during the wait. This dependency is stated wherever the build order appears.

**Alternatives considered:** **Card-to-card** (ADR-0006, superseded) — its rules were correct for it, but it charges the customer friction at the exact moment doubt is highest, charges the operator a daily manual match, and cannot do one payment for a multi-item cart. **Gateway with no manual fallback** — rejected: it makes the shop unable to sell until Enamad clears, and hands every gateway outage a full stop with no way to take a customer's money; the fallback is a few hours of admin action against a category of downtime that is routine here. **Two gateways from the start** — rejected: an unapproved second provider is speculative, doubles the Enamad and settlement paperwork, and the interface that would make switching cheap is itself deferred until a second implementation exists ([ADR-0013](0013-payment-provider-interface-deferred.md)).

**Consequences:** Every rule above is a money-path test and non-negotiable: redirect-parameter forgery, amount mismatch, duplicate callback, and the lost-callback inquiry each have a named test. The inquiry beat task is not optional infrastructure — a deploy without it running is a deploy that can silently eat a payment.
