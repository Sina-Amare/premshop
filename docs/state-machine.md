# PremShop — State Machine Specification

> **Firmness (owner calibration, 2026-09-01).** Settled now: the 7-status item list, the 5-status payment list, transitions only through services, illegal transitions raise, the executed-Refund gate on REFUNDED, the event-row-inside-the-transaction rule, and the four payment non-negotiables in §2 (verify is the sole source of truth, amount must match, confirm is idempotent, `abandoned` only via inquiry). The per-transition guards/side-effects and the event catalog harden at the step that implements them (item machine → S4a, manual fallback → S4b, gateway machine → S5, notification consumers → S6/S8); until then they are the best current draft. A mid-step discovery that a row here is wrong is a contract conversation, not a workaround.

Scope: OrderItem machine, Payment machine, event catalog, concurrency rules, test list. Implements ADR-0003 (transitions through services), ADR-0005 as amended (money paths, discount codes), ADR-0018 (persistent cart + guest checkout), ADR-0019 (payment gateway — supersedes the card-to-card design of ADR-0006), ADR-0020 (discount codes), plus D7–D11 and D17–D18. All transitions live in `orders/services.py` and `payments/services.py`; any status write outside a service method is a code-review reject.

Conventions used below:

- `PP` = PENDING_PAYMENT, `Q` = QUEUED, `AI` = AWAITING_INPUT, `DEL` = DELIVERED, `RR` = REPLACEMENT_REQUESTED, `CAN` = CANCELLED, `REF` = REFUNDED.
- Every allowed transition: runs inside `transaction.atomic()` with `select_for_update()` on the row, validates the (from, to) pair against this matrix, raises `InvalidTransition` otherwise, writes one `OrderItemEvent` row **inside** the transaction, and calls `events.emit(...)` via `transaction.on_commit()`.
- `compute_due_at(confirmed_at, delivery_hours, schedule)` is the single pure SLA function (D7): wall-clock add, snap **forward** to next support window if outside one, hard cap `confirmed_at + 48h`. The cap applies at computation time only; SLA pauses may legitimately push `due_at` past it.

## 1. OrderItem machine

### 1.1 Diagram

```mermaid
stateDiagram-v2
    [*] --> PENDING_PAYMENT: order created (web/bot)
    [*] --> DELIVERED: legacy backfill (channel=legacy, A14)

    PENDING_PAYMENT --> QUEUED: payment verified
    PENDING_PAYMENT --> CANCELLED: expired / customer / operator

    QUEUED --> AWAITING_INPUT: operator requests info (SLA pause)
    AWAITING_INPUT --> QUEUED: input received (SLA resume)
    QUEUED --> DELIVERED: operator delivers
    QUEUED --> CANCELLED: cancel approved / supply failure
    AWAITING_INPUT --> CANCELLED: input timeout (operator-only) / cancel approved

    DELIVERED --> REPLACEMENT_REQUESTED: warranty claim / re-delivery need
    REPLACEMENT_REQUESTED --> DELIVERED: replacement delivered (A10a, new DeliveryField generation)
    REPLACEMENT_REQUESTED --> DELIVERED: claim rejected (A10b, no new generation)
    REPLACEMENT_REQUESTED --> CANCELLED: replacement impossible (warranty_refund)

    CANCELLED --> REFUNDED: refund executed (Refund row)
    CANCELLED --> QUEUED: operator revive (payment verified late, or erroneous cancellation)

    REFUNDED --> [*]
    note right of DELIVERED
        Replacement cycle: DELIVERED → REPLACEMENT_REQUESTED → DELIVERED
        may repeat any number of times ("bans are routine").
        Each pass writes a NEW generation of DeliveryField rows
        (old rows kept, is_current=False).
    end note
    note right of CANCELLED
        CANCELLED with no money owed = terminal.
        CANCELLED with money owed → REFUNDED once

    end note
```

Forbidden-reason glossary: **unpaid** = payment not verified; **paid** = money already taken, cannot regress to pre-payment; **undelivered** = replacement states only make sense after a delivery; **resume-first** = must return to QUEUED (restoring the SLA clock) before delivering; **via-replacement** = post-delivery problems route through REPLACEMENT_REQUESTED only (brief: "پس از تحویل: فقط از مسیر گارانتی و تعویض"); **via-CANCELLED** = REFUNDED is only reachable from CANCELLED with an executed Refund row (D2); **loop-only** = RR resolves only to DELIVERED or CANCELLED; **revive-to-QUEUED** = the only exit from CANCELLED besides REFUNDED is the operator revive, and it lands on QUEUED because it is guarded by a **verified** payment; **terminal** = REFUNDED is final; **no-op** = self-transitions are forbidden (holiday SLA annotations and `orders.extend_due_at` write an `OrderItemEvent` with `from_status == to_status` but are not status transitions — see §4.6 and below).

Not a transition (by decision D1): a customer cancellation **request** on a Q/AI item sets `cancellation_requested_at`, emits `item.cancellation_requested`, shows a queue badge; the item's status does not change until the operator approves (A6/A8).

Also not a transition: `orders.extend_due_at(*, item, new_due_at, note, actor='operator')` — legal only in QUEUED; writes an annotation `OrderItemEvent` (`from_status == to_status == QUEUED`, note) and emits `item.supply_delayed` (customer delay notice, C6). This service, `compute_due_at`, and the pause/resume arithmetic (§4.6) are the **only** writers of `due_at`.

## 2. Payment machine

Statuses: `created`, `initiated`, `verified`, `failed`, `abandoned` (ADR-0019). Refunds are **not** payment statuses (D2) — the Refund model records each outbound refund, by gateway API or bank transfer, and drives A12 above. `Payment.method` (`gateway` | `manual`) records how the money arrived; it is a record field, never a branch in the state machine — both methods produce the same `verified` payment and the same item transitions.

### 2.0 Non-negotiables

Four rules. They are the reason this machine exists; a change to any of them is an ADR, not a patch.

1. **Server-to-server verify is the only source of truth.** The browser redirect back from the gateway carries parameters that are attacker-controllable — a customer can hand-edit `status=OK`, `amount`, `refnum` and re-open the URL. Those parameters are used for exactly one thing: identifying **which** payment row to look at. Confirmation comes only from the verify call made by our server to the gateway's API, over a channel the customer cannot touch. A callback whose parameters claim success while verify says otherwise confirms nothing.
2. **Amount must match.** Verify's reported amount is compared against `payment.amount` (= `order.total_amount`) and then **discarded — it is never stored**. There is no `paid_amount` column: a matching amount is by definition `payment.amount`, and a mismatching one never becomes a payment at all. Any difference — under or over — sends the payment to `failed` with `failure_reason=amount_mismatch` and alerts the operator. We never deliver an order for less than it costs, and we never silently pocket an overpayment.
3. **Confirm is idempotent, and there is exactly one confirmer.** `payments.confirm_payment(payment, ...)` is the internal, row-locked, idempotent helper and the **sole emitter** of `payment.verified`. Its mechanism is a **lock-and-re-read, and nothing else**: take `select_for_update()` on the Payment row, re-read `status` **under that lock**, and return the payment unchanged if it is already `verified`. Never an unlocked `if not payment.verified` on a value read before the lock — that check is exactly the race it is supposed to close. Both `verify_payment` (callback *and* inquiry) and `record_manual_payment` route through it — no second path writes `verified`. Repeated callbacks, browser refreshes, double submits, and the inquiry task racing the callback therefore all collapse under that one lock. Result: one confirmation, one set of item transitions, one `payment.verified` event — always. (`Payment.idempotency_key` is *not* this guarantee: it is the gateway-facing key from P-A1 and takes no part in confirmation.)
4. **`abandoned` is reachable only from `initiated`, only by the inquiry beat task**, and only after the gateway itself answers that the payment was never completed. Nothing may guess at abandonment from a timeout alone — a silent customer and a paid-but-lost callback look identical from our side, and only the gateway can tell them apart.

### 2.1 Diagram

```mermaid
stateDiagram-v2
    [*] --> created: checkout (order + payment, one transaction)

    created --> initiated: gateway token obtained, customer redirected
    created --> verified: operator manual fallback (method='manual')

    initiated --> verified: server-to-server VERIFY says paid (callback OR inquiry beat)
    initiated --> failed: verify says failed, gateway says cancelled, or amount mismatch
    initiated --> abandoned: inquiry beat — gateway says never completed

    verified --> [*]
    failed --> [*]
    abandoned --> [*]

    note right of initiated
        Browser-returned parameters NEVER confirm anything.
        They name the payment; verify decides its fate.
    end note
    note right of failed
        A customer retry is a NEW Payment row (P-A1),
        not a transition back. failed/abandoned are terminal.
    end note
```

### 2.2 Transition grid (every ordered pair)

| from \ to | created | initiated | verified | failed | abandoned |
|---|---|---|---|---|---|
| **(creation)** | **P-A1** | not-yet-initiated | unverified | nothing-failed | inquiry-only |
| **created** | no-op | **P-A2** | **P-A6** (manual only) | not-started | inquiry-only |
| **initiated** | one-way | no-op² | **P-A3** | **P-A4** | **P-A5** |
| **verified** | terminal | terminal | **idempotent no-op³** | terminal | terminal |
| **failed** | terminal | retry-is-a-new-payment | terminal | no-op | terminal |
| **abandoned** | terminal | retry-is-a-new-payment | terminal | terminal | no-op |

² Asking to pay again while `initiated` (customer hits back, then clicks pay) reuses the existing token if it is still valid and otherwise replaces `authority` in place on the same row — a field update, not a transition, no event. `authority` is UNIQUE, which costs nothing here (the replacement is on the same row) and turns an impossible token collision into a loud failure instead of a silent mismatch.
³ Calling `confirm_payment` on an already-`verified` payment returns success, changes nothing, emits nothing, transitions no items. See §2.3 P-A3 and non-negotiable 3.

Forbidden-reason glossary: **not-yet-initiated** = a payment is born in `created`; only P-A2 (a real gateway token) may make it `initiated`. **unverified** = `verified` is produced only by a verify call (P-A3) or the operator's manual fallback from `created` (P-A6) — never at creation, never from `failed`/`abandoned`, where the money question is already settled. **nothing-failed** / **not-started** = a payment that never reached the gateway has nothing to fail; a token request that errors leaves the row in `created` for a retry. **inquiry-only** = non-negotiable 4 — `abandoned` comes from `initiated` via the inquiry task and nowhere else. **one-way** = a payment never returns to `created`. **retry-is-a-new-payment** = after `failed` or `abandoned` the customer retries by creating a fresh Payment (P-A1); legal because the partial unique on `order_id` covers only `created`/`initiated`. **terminal** = `verified`, `failed`, `abandoned` are final. **no-op** = self-transitions are forbidden.

| **P-A4** | initiated → failed | Verify returns a failure, the gateway reports the transaction as cancelled/failed by the customer, or the verified amount did not match | system | Under lock, status is still `initiated` — a payment that won the race to `verified` is never downgraded | `failure_reason` stored (`gateway_failed` \| `cancelled_by_customer` \| `amount_mismatch`), `failed_at = now()`; **the order stays PENDING_PAYMENT and its items stay PP, payable** — `fail_payment` cancels nothing and stamps no `expired_unpaid`; the retry link in the failure message depends on exactly that; `amount_mismatch` additionally alerts the operator | `payment.failed` |
| **P-A5** | initiated → abandoned | Inquiry beat task (§2.4): the payment is past the inquiry threshold and the gateway's status API answers that it was never completed | system | Under lock, still `initiated`; **a negative answer from the gateway is required — a timeout alone is not one** (non-negotiable 4) | `failure_reason = 'abandoned'`, `failed_at = now()` (the same column serves `failed` and `abandoned`); **`abandon_payment` transitions the payment and nothing else** — items stay PP (the A3a unpaid-order sweep cancels them at `unpaid_order_ttl_hours` if the customer never comes back — it may now do so, the payment having left `initiated`); the row leaves the live set, so a retry may create a new Payment | none — the customer already saw the gateway page fail or walked away, and the operator has no action; a beat-task outcome with no consumer emits nothing |
| **P-A6** | created → verified | **Manual fallback (ADR-0019 — gateway rail with an operator-only manual fallback):** operator-only admin action «ثبت پرداخت خارج از درگاه» — money received outside the gateway (during the Enamad wait, or a gateway outage). `payments.record_manual_payment` performs the checks, then routes through `payments.confirm_payment` like every other confirmation | operator | Staff; **free-text `note` required and non-empty — the action refuses without it**; payment must still be `created` (never an `initiated` one: an in-flight gateway attempt is settled by verify or inquiry first, so the operator cannot race the gateway). Not customer-facing: no receipt upload, no unique amount, no customer submission | `method='manual'`; `verified_at = now()`, `matched_by = request.user` (the operator), `note` stored; **every PP item runs A2 in the same transaction** — identical to P-A3; the payment is listed separately in the reconciliation view (`method='manual'` filter) | `payment.verified` (payload `method='manual'`) |

**Money display at the checkout boundary.** The checkout summary — computed server-side and rendered **before** submission, so the customer approves the same numbers the order is then created from — is the last screen before real money moves, so it follows the money rules already in force (`docs/design-language.md`, ADR-0016): Persian digits, ASCII thousands separator, toman only — never rial, the currency word set lighter than the numeral, tabular figures so the column aligns. It shows **three distinct ledger lines — جمع کل (subtotal), تخفیف (discount, negative), مبلغ قابل پرداخت (total)** — using the ledger-line component, never a single opaque number. The amount rendered here and the amount sent to the gateway are the same server-computed `order.total_amount`; nothing on this screen is arithmetic done in the browser.

### 2.4 Lost-callback recovery (mandatory)

The failure this exists for: the customer pays, the network dies before the redirect, the callback never arrives. Money taken, order dead. Without recovery that is a silent loss and an angry customer.

A Celery beat task sweeps payments still `initiated` past `SiteSetting.gateway_timeout_minutes` (default 15) and calls the gateway's inquiry/status API for each. This is the payment-side clock and the lost-callback net; the order-side clock — `SiteSetting.unpaid_order_ttl_hours` (default 24), which lets the unpaid-order sweep cancel a PENDING_PAYMENT order (A3a) — is a separate field with a separate job, and the sweep defers to this one by skipping any order with an `initiated` payment.

| Gateway answer | Action |
|---|---|
| paid | Run the ordinary verify path — **P-A3, exactly as a callback would**: same amount check, same item transitions, same `payment.verified`. Nothing about the confirmation differs because a task rather than a browser triggered it. |
| never completed / failed | **P-A5** → `abandoned` (or P-A4 `failed` when the gateway distinguishes an explicit failure). |
| still pending at the gateway | Leave it. Re-inquire on the next sweep. |
| inquiry call errors or times out | Leave it, log, retry next sweep. **Never** treat an unreachable gateway as an unpaid customer. |

The sweep is idempotent by construction: everything it does routes through the same locked, idempotent `confirm_payment` as the callback (§4.7).

## 3. Event catalog

`events.emit(name, payload)` runs in `transaction.on_commit`; its only job is creating Notification outbox rows (D18). `OrderItemEvent` rows (the audit trail / public timeline) are written **inside** the transaction and are independent of this catalog. Customer channels: email always; Telegram additionally when linked. Operator alerts: **both** Telegram and email (D17). All customer-facing texts carry no credential values (D13); delivery/replacement notices additionally carry the single-use 72h delivery link — a bearer capability, not content — scrubbed from Sentry and truncated in access logs (ADR-0008). Auth OTP sends are not domain events — they go straight through the channel senders (they must be immediate and never deduped). Dedupe keys follow one rule: `{occurrence}:{recipient}:{channel}`, where recipient is the user id or the literal `op` (operator) — so an operator alert on payment 1041 is `pay:1041:verified:op:telegram`. **This section is the canonical dedupe-key registry**, and the table below is its complete list of prefix families — eleven, not five: `evt:` (any keyed OrderItemEvent), `pay:`, `refund:`, `renew7:`, `renew0:`, `delay:`, `remind:`, `hpause:` / `hresume:`, `signin:`, `cancelreq:`, `overdue:`. Any other document listing key shapes points here rather than enumerating its own subset; a new family is added here first. Transitions that notify emit an event; transitions that don't, don't — there are no consumer-less events. Applied to the gateway machine, that rule deletes three names: **`payment.initiated` is not emitted** (P-A2 — the customer is at the gateway, the operator has nothing to do), **`order.created` is not emitted** (A1 — the operator's new-order alert moved to `payment.verified`, because an unpaid order is not news), and P-A5 `abandoned` emits nothing. The same rule deletes `telegram.linked`: the bot already replies in line when an account is linked, so the event had no consumer either. The card-to-card family — `payment.submitted`, `payment.rejected`, `payment.expired` — is gone with ADR-0006. This catalog is the canonical event registry across all plan artifacts.

## 4. Concurrency rules

**4.1 Lock scope and ordering.** Every item transition: `SELECT ... FOR UPDATE` on that OrderItem only. Every payment transition: `FOR UPDATE` on the Payment, and when it cascades to items (P-A3/P-A6 + revive), lock the Payment **first**, then its OrderItems ordered by `pk` — one consistent lock order, no deadlocks. Never lock the Order row (nothing transitions on it). The one exception in the checkout path: A1 also takes `select_for_update` on the DiscountCode row to increment `used_count` and write the `DiscountRedemption`, and takes it **before** inserting the order — a code, then an order, then a payment, then the cart clear, always that order.

**4.2 Transaction boundary.** One `transaction.atomic()` per user-visible action, even when it spans machines: "confirm payment" = payment P-A3 (or P-A6) + N × item A2 + N+1 OrderItemEvent-adjacent writes, all-or-nothing. "Revive" = `payments.revive_order(payment)`: the A13s of every guard-passing item, one transaction, reading an already-`verified` payment. "Cancel with refund" = `payments.cancel_with_refund`: item cancel + Refund-row creation, one transaction. "Checkout" = `payments.checkout`: discount validation + `used_count` increment + the `DiscountRedemption` row + `orders.place_order` + Payment creation (P-A1) + **deleting the customer's CartItem rows**, one transaction — so a single-use code cannot be spent twice concurrently, an order never exists without its payment row, and a cart is never both consumed and still sitting there. DeliveryField writes and generation supersession (A10a) are inside the delivery transaction.

**The gateway HTTP call is deliberately outside that transaction.** `payments.checkout` commits the order and its `created` payment first, and only then calls the gateway for a token (P-A2). A gateway that takes eight seconds to answer would otherwise hold the DiscountCode lock and the order's row locks for eight seconds, and a gateway that hangs would hold them until the connection timeout — database locks pinned to a third party's latency. The cost of moving the call out is that a failed token request leaves an order in PENDING_PAYMENT with no redirect; that is the correct outcome, not a leak — the order is payable, the customer retries from its pay page, and A3a eventually cancels it if they never do. The same rule applies to the verify call: the HTTP request happens first, the transaction opens after the answer is in hand.

**4.3 Validate-under-lock.** Status is re-read after acquiring the lock and validated against the matrix there — never trusted from the form/page that rendered the button. `InvalidTransition` carries (from, to) for the log.

**4.4 on_commit enqueue (D18).** `events.emit` is registered with `transaction.on_commit`; it creates outbox rows which the Celery outbox worker picks up (status/attempts/backoff). Notification failure can never roll back a delivery (brief §8). Rollback ⇒ no emit ⇒ no ghost notifications.

**4.5 Double-click / two-tab behavior per operator action.**

| Action | Second click / second tab outcome |
|---|---|
| Return from gateway / refresh the callback URL | Idempotent success (P-A3). Every extra call finds `verified` under lock and returns the same result page. Zero duplicate events, zero duplicate item transitions. |
| Record manual payment (P-A6) | Second click finds `verified` → idempotent success, no second set of item transitions, no second `payment.verified`. |
| Deliver (A5) | Second request finds status DELIVERED under lock → `InvalidTransition` → panel returns an HTMX 409 partial: «این سفارش قبلاً تحویل شده» + refreshed row. No second DeliveryField generation. |
| Replacement deliver (A10a) / reject claim (A10b) | Second request finds DELIVERED → same 409 partial. Exactly one new generation per A10a pass; A10b never writes one. |
| Request info (A4) | Second click finds AI → `InvalidTransition` → panel refreshes the row silently (operator's intent already satisfied). |
| Cancel / approve cancellation | Second click finds CAN → 409 partial «قبلاً لغو شده». |
| Revive | Second click finds the items already Q → `InvalidTransition`, panel refreshes. The payment is untouched either way. |
| Mark refund executed (A12) | Second click finds REF → 409 partial. `Refund.executed_at` write is guarded by `executed_at IS NULL` under lock. |

Customer-side races (callback vs. unpaid-order sweep; input submit vs. operator cancel): the beat/operator holds the lock first or second; loser's guard fails cleanly; the beat treats a lost race as a skip, the customer gets a Persian error page telling them the current state. The A3a sweep additionally refuses to cancel an order with an `initiated` payment, so a customer mid-gateway is never cancelled out from under.

**4.6 Holiday mass pause/resume (D7).** Reuses the `sla_paused_at` arithmetic without a status change. Pause: beat-driven service iterates Q items with `sla_paused_at IS NULL`, **per-item transactions** (no long table lock), sets `sla_paused_at = now()`, writes an annotation `OrderItemEvent(Q→Q, system, note="holiday pause")`, emits `sla.holiday_paused`. AI items are already paused — skipped. Resume: for each item with `sla_paused_at NOT NULL` and status Q, `due_at += now() − sla_paused_at`, clear, annotate, emit. Interaction guards: A4 does not overwrite an existing `sla_paused_at`; A7 re-stamps `sla_paused_at = now()` when `holiday_pause_sla` is still on; A5 refuses to deliver a paused item (resume first). Consequence to document: `sla_paused_at NOT NULL` no longer implies status AI.

**4.7 Callback vs. inquiry race.** The one genuinely concurrent path in the payment machine: the customer's redirect arrives at the very moment the inquiry beat task (§2.4) is asking the gateway about the same `initiated` payment. Both then try to confirm it, in two processes, against the same row.

The rule: **both go through `payments.confirm_payment`, which takes `select_for_update` on the Payment first, re-reads status under the lock, and returns unchanged if it is already `verified`.** Whichever transaction wins the lock performs P-A3 — amount check, item A2 cascade, `payment.verified` — and commits; the loser blocks, wakes to `verified`, and does nothing. Net effect: one confirmation, one set of item transitions, one event, whichever order they arrive in. The row lock provides the mutual exclusion; the idempotent re-read makes the loser harmless. No advisory locks, no distributed lock, no Redis — one `FOR UPDATE` covers it.

Same mechanism covers the other pairs: two callbacks (customer refreshes), two inquiry sweeps overlapping, a callback racing P-A4. The only ordering the machine forbids is a `verified` payment being pushed to `failed`/`abandoned` — P-A4 and P-A5 both re-check `status == 'initiated'` under the same lock, so a late failure report cannot undo a confirmed payment.

*One live payment per order* rides on the same section: the partial unique on `order_id WHERE status IN ('created','initiated')` is the invariant; the ordinary `IntegrityError` from a concurrent double-checkout is the concurrency control. A retry after `failed`/`abandoned` inserts cleanly because those rows are outside the index. No table locks, no sequences.

**4.8 Delivery-link redeem.** The token is redeemed under the item's `select_for_update` lock: validate hash + expiry + `used_at IS NULL`, stamp `used_at`, render the masked view. A concurrent second open loses the race and gets the login page — single-use holds the way Redis `GETDEL` does for link tokens. Invalid/expired/used → uniform 404, rate-limited per IP.

## Concerns

Flagged, not deviated from:

1. **D18 vs. classic outbox:** creating outbox rows in `on_commit` (not inside the transaction) means a process crash in the gap silently drops that occurrence's notifications. Acceptable at this volume — the overdue alarm, operator queue, and dead-man heartbeat are the backstops — but worth one line in the ADR so nobody later "fixes" the ordering without knowing it was chosen. **Accepted at owner review (2026-09-01) — record in the S1 ADR.**
2. **`created` payments on cancelled orders are never cleaned up.** A customer who checks out and never clicks «پرداخت» leaves a `created` row that no beat task ever touches. Deliberate: the live-payment index is scoped per order, so the row blocks nothing, and a cleanup job would be machinery for a harmless row. Flagged so nobody later reads it as an oversight.
3. **A gateway outage stalls everything, and the manual fallback is the only door.** If the gateway is down, `payments.start_gateway_payment` cannot mint a token and no customer can pay themselves — P-A6 (operator records the money) is the entire contingency. That is the ADR-0019 bet: two payment paths from day one, and the second one is a human. Revisit if outages become frequent enough that the operator is the bottleneck.
4. **Cancelling an order with an in-flight `initiated` payment is refused, not queued.** The A3a unpaid-order sweep skips such orders entirely, however far past `unpaid_order_ttl_hours` they are, and waits for the inquiry task to settle the payment first. Consequence: a gateway that never answers an inquiry leaves an order stuck in PP indefinitely. The overdue digest is the backstop — the operator sees it and settles it by hand.
5. **Holiday pause weakens an invariant:** after D7's reuse of `sla_paused_at` on QUEUED items, `sla_paused_at NOT NULL` no longer implies AWAITING_INPUT. Guards in §4.6 and tests 36–37 cover it, but panel code must filter the «منتظر مشتری» tab by status, never by `sla_paused_at`.
